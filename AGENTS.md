# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

## Project Overview

This is a Java Spring Boot project demonstrating customizations for the Camunda AI Agent connector. The project showcases how to extend and customize the Camunda AI Agent functionality with custom conversation storage, agent initializers, and custom bean processing.

## Build and Development Commands

```bash
# Build the project
mvn clean compile

# Run tests
mvn test

# Run integration tests
mvn verify

# Run the application locally
mvn spring-boot:run

# Package the application
mvn clean package
```

## Testing

`CustomizationsContextTest` is a Spring context smoke test (PostgreSQL Testcontainer, requires Docker; no Camunda cluster needed). It checks that the custom initializer, conversation store, chat model factory and system prompt contributor are wired, and that `MyConversationContext` round-trips on the connector runtime's object mappers. `src/main/frontend/src/types/conversation.test.ts` (Vitest, run by `mvn test` and `npm test`) parses a captured API response with the UI's Zod schema; refresh `__fixtures__/conversation.json` when the backend's message format changes. End-to-end verification is manual: start the app and exercise the agent through the UI.

## Architecture

The project follows Spring Boot conventions with these key customization points:

### Core Components

- **AiAgentRuntimeApplication**: Main Spring Boot application class
- **LoggingAgentInitializer** / **AgentInitializerDecoratingBeanPostProcessor**: Decorates the connector's default `AgentInitializer` bean with logging (a `BeanPostProcessor` wraps the existing bean, so the connector's implementation class is not referenced)
- **ConversationContextSubTypesBeanPostProcessor**: Registers `MyConversationContext` as a Jackson subtype on every `ObjectMapper` bean (the connector runtime's mappers are not reachable through Boot's Jackson customizers)
- **MyCustomSystemPromptContributor**: `SystemPromptContributor` bean that appends the current date and the BPMN process id to the agent's system prompt
- **UppercaseChatModelFactory** / **UppercaseChatModel** (`chatmodel/`): Custom chat model provider (`custom` provider type `uppercase`); builds a native OpenAI model from the provider parameters and upper-cases its text responses

### Custom Conversation Storage

Located in `src/main/java/io/camunda/example/aiagentruntime/memory/conversation/`:

- **MyConversationStore**: Custom conversation store (`TYPE = "my-conversation"`). Implements the new SPI: `createSession`, `onJobCompleted`, `onJobCompletionFailed`.
- **MyConversationSession**: Per-turn session implementing `loadMessages` (recursive CTE chain walk) and `storeMessages` (append-only delta insert).
- **MyConversation**: Parent entity — one row per logical conversation; holds process metadata and the `lastKnownHeadId` projection updated post-commit in `onJobCompleted`.
- **MyConversationTurn**: Child entity — one row per agent turn; chained via `parentId`; stores only the turn's message delta.
- **MyConversationRepository**: JPA repository for the parent.
- **MyConversationTurnRepository**: JPA repository for turns; contains the recursive CTE that walks `parentId` from a given head back to the root.
- **MyConversationContext**: Storage cursor — `(conversationId, recordId)` where `recordId` points to the head turn.

### Database

- PostgreSQL with Flyway migrations.
- Migration: `src/main/resources/db/migration/V1__init_my_conversation.sql`
- Tables:
  - `conversations`: parent rows (id = conversationId, process metadata, `last_known_head_id`).
  - `conversation_turns`: append-only chain (id, parent_id, conversation_id, element_instance_key, job_activated_at, messages JSON delta).
- All UUID PKs are UUIDv7, generated by Hibernate via `@UuidGenerator(style = VERSION_7)`.
- Docker Compose setup for local PostgreSQL instance.

### Configuration

- **application.yml**: Base configuration (port 8181)
- **application-dev.yml**: Development profile
- **application-dev-mcp-client.yml**: MCP client development profile
- Uses Spring Boot Docker Compose support for local development

## REST API for Conversations

The project includes a REST API for accessing conversation data:

### API Endpoints

- `GET /api/conversations` - List all conversations that have a committed head (`last_known_head_id` not null), most recently updated first.
- `GET /api/conversations/{conversationId}` - Get a specific conversation with its full message history (reassembled by walking the turn chain from the projection's head pointer).

### API Models

- **ConversationListDto**: Summary view for the conversation list (id, conversationId, timestamps, bpmnProcessId, first user message preview).
- **ConversationDto**: Full conversation including the reassembled message list.
- **ConversationDto.JobContextDto**: Process-level metadata snapshotted at conversation creation. Per-turn `elementInstanceKey` lives on the chain row, not here.

### Frontend Development Setup

## Custom Agent Configuration

To use the custom conversation store, configure the agent with:
- Memory storage type: "Custom Implementation"
- Implementation type: "my-conversation"

To use the custom chat model: Provider "Custom Implementation", provider type `uppercase`, parameters `={apiKey: "{{secrets.OPENAI_API_KEY}}"}`. Use the v2 hybrid element templates only (no L4J / v1).
